# Outrim — Lovable build guide

Version: 0.1 · 19 October 2026 · Status: specification for a new project; not implemented

## 1. Start here

Build Outrim as a browser-based persistent multiplayer strategy game with a 2.5D hex world. Players establish industrial frontier bases, produce Alloy, construct buildings, train units, dispatch expeditions, gather resources and raid rival bases. The world is the primary game screen; management panels open over it.

The owner has selected **Supabase, email/password authentication, no research, and no blockchain actions for the first version**. Solana is the possible future blockchain direction. It introduces no wallet, token, payment, withdrawal, NFT or ownership requirement into this build.

This package is intended to be uploaded to a **new Lovable project**, then handed back as source code for engineering completion. It is a build specification, not a request to modify the current application's database or connect its worker to Supabase.

| Status | Decision |

| Owner requirement | Supabase backend; email/password signup and login |
| Owner requirement | No research system |
| Owner requirement | Focus on gameplay; no blockchain actions |
| Working design | One base per player per world; one initial world |
| Working design | Timestamp-based travel, gathering and construction; server-resolved combat |
| Working design | Internal Alloy and Sparks; no external value or redemption |

Working design decisions make the prototype implementable. Record deliberate changes in the new project's decision log and update the affected specifications together. Numeric balance is an alpha baseline, not inherited Hive behavior or a tested economy.

## 4. New-project technical direction

- React + TypeScript frontend using the stack generated by the new Lovable project; do not require this repository's Next.js runtime.
- Supabase Auth for email/password, verification, password reset and sessions.
- Supabase PostgreSQL as authoritative gameplay persistence, with migrations committed to source.
- Transactional PostgreSQL functions for commands and completion processing; Edge Functions may validate transport and call one transactional function.
- Supabase Cron invokes a bounded job processor. Work survives disconnects and process restarts.
- Private Supabase Realtime channels carry authorized invalidations; durable reads recover state after reconnect.
- Canvas/WebGL renders the map, with ordinary accessible HTML for controls, dialogs and alternatives. Start with a bounded Canvas renderer; measure before adding a larger rendering engine.
- Static, versioned gameplay definitions have a single server authority. Generate browser-safe display definitions and test parity.
- GitHub/source export and reproducible migrations are required handoff artifacts.

Prefer a dedicated Supabase project owned by the game owner for development, followed by separate staging/production projects. Choose the backend before creating persistent data. Lovable documents its managed Cloud backend and connecting an independently owned Supabase project as distinct options; switching requires planning. [Lovable Supabase integration](https://docs.lovable.dev/integrations/supabase)

Use the chosen project's existing package manager and lockfile. Record exact tool/runtime versions in the new README. Do not copy this repository's dependency pins indiscriminately.

## 5. Delivery sequence

1. **Foundation:** source sync, design system, email authentication, schema/security tests, versioned world generation and atomic world joining.
2. **Playable base:** map, own base, production, Secure Haul and one construction queue.
3. **Expeditions:** unit training, travel, gathering, return and operation reports.
4. **Competition:** scouting, protected-player rules, deterministic raids and concurrency tests.
5. **Modules:** stacks, cache purchase/opening, equipment, tuning and dismantling.
6. **Hardening:** Realtime recovery, accessibility, assets, mobile performance, load tests and deployment evidence.

Each phase must have persisted behavior and passing negative authorization tests before the next. A polished preview with simulated balances is a design prototype, not a completed phase.

## 6. Completion definition

Two independently authenticated players can join the world, obtain distinct bases, construct, train, gather, scout, fight and inspect durable reports. Logging out or closing every tab does not stop accepted actions. Repeated requests and duplicate job execution do not duplicate rewards. A player cannot modify another player's state or read private resources, units, commands, jobs or reports. Reconnect restores authoritative state after missed events.

The full world contains exactly 62,500 coordinates. Atomic admission enforces the 1,000-base limit. The frontend renders and fetches bounded map regions. Full-capacity simulation and concurrent-session testing have separate recorded results. Production readiness requires the validation checklist; a Lovable preview alone is insufficient evidence.
